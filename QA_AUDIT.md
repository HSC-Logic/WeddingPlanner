# Production-readiness QA audit

Audit date: 2026-09-12  
Scope: repository, configured build and validation tools, Chromium desktop/mobile projects, production preview, IndexedDB persistence, native service worker, and all user-facing modules.

## Executive summary

The audit confirmed and fixed 22 defects: 6 high, 12 medium, and 4 low. The highest-risk findings were incomplete backup validation, an unusable restore path after clearing all data, orphaned cross-module records, seating corruption after RSVP changes, and forms that discarded input after failed IndexedDB writes. Regression coverage was added for database migration and failure handling, backup recovery, record integrity, seating synchronization, accessibility, responsive reflow, and representative Hall Designer load.

Final checks pass from a clean `npm ci`: formatting, lint, TypeScript, 44 unit tests, 16 applicable Playwright tests, the production build, and the npm vulnerability audit. Twelve Playwright cases are intentionally skipped in the mobile project because equivalent mobile-specific coverage exists or the workflow is desktop-only. The production shell was also loaded online, placed under service-worker control, and reloaded offline in Chromium.

No confirmed defects remain. Cross-browser execution outside Chromium, real mobile hardware gestures/keyboards, browser-driven install prompts, storage eviction, concurrent editing from multiple tabs, PDF/PNG Hall export (the implementation supports SVG and print), and GitHub's Linux runner were not available locally and remain unverified.

## Security and privacy findings

- No `dangerouslySetInnerHTML`, embedded secrets, analytics, trackers, or automatic network transfer of wedding records were found.
- CSV escaping neutralizes cells beginning with `=`, `+`, `-`, `@`, tab, and carriage return; its unit tests pass.
- Vendor URLs are allowlisted to safe HTTP(S) schemes and external links use safe opener behavior.
- Strict backup parsing rejects unknown keys and bounds file size, collection size, text length, coordinates, money and counts before any write. Replacement is transactional, so validation failure leaves current data unchanged.
- `npm audit --json` reported zero known vulnerabilities after the clean install.
- The service worker caches same-origin static responses only; private records remain in IndexedDB. The sole application console error contains an error message and component stack, not record data.

## Accessibility and responsive findings

Automated axe-core scans found no WCAG 2.1 A/AA violations on Dashboard, Guests, Seating, Settings, Hall Designer, or the shared modal after fixes. Keyboard tests cover modal initial focus, trapping, Escape and focus restoration. The interface includes a skip link, landmarks, labelled forms and switches, responsive navigation excluded from focus while closed, table/chart text equivalents, reduced-motion styling, and an accessible Hall element/property list with numeric controls.

Horizontal reflow was programmatically checked in light and dark themes at 320×568, 360×800, 390×844, 412×915, 768×1024, 1024×768, 1280×720, 1440×900 and 1920×1080. Playwright also covers mobile navigation and the Hall Designer's mobile read-only state.

Automated rules and Chromium keyboard checks do not replace a full screen-reader study, real-device touch testing, mobile virtual-keyboard testing, or expert visual contrast inspection on every state.

## Performance and large-data findings

The production code split removed Vite's large-chunk warning: initial JS is 354.50 kB (104.97 kB gzip), and Hall Designer loads as a separate 233.28 kB chunk (72.40 kB gzip). Unit performance coverage validates 100 Hall objects, 50 flows and 1,000 guests in under one second in the test environment, plus non-overlapping placement of 100 tables. Undo history is bounded and pointer movement commits once at interaction end.

The requested 500-task and 500-expense browser datasets were inspected through the aggregation implementation but were not separately benchmarked in a browser profile. No material synchronous bottleneck was reproduced there.

## Unreproduced concerns and limits

- A suspected duplicate startup state update was checked in the exact source and was not present; it was an artifact of concatenated command output.
- Chromium was the only installed Playwright engine. Firefox, WebKit/Safari, assistive technologies, real mobile devices, high-DPI hardware, browser storage eviction, interrupted operating-system writes, and multi-tab simultaneous edits were not executed.
- CI configuration and clean installation were inspected locally on macOS. GitHub Actions/Linux was not triggered, so Linux execution is unverified even though the lockfile-selected Oxlint binding loaded locally.
- The browser's installability prompt is controlled by browser policy and was not invoked. Manifest structure, icon presence, worker control, cache refresh path and offline reload were verified.
- Hall output provides full-plan SVG export and print CSS. Dedicated raster PNG and generated PDF exporters, A3 controls, and a separate guest-directory layer are not implemented features, so those requested scenarios could not be tested as existing behavior.
- Automatic placement is a deterministic heuristic and is labelled as a suggestion, not as an optimal or safety-certified layout. The UI states that it is a planning aid rather than building/fire approval.

## Recommendations

1. Run the Playwright suite in CI with Chromium, Firefox and WebKit, and keep the existing fast deploy gate.
2. Conduct a real-device and screen-reader pass before a public launch, especially Hall touch gestures, 200% zoom and mobile keyboards.
3. Split the large application components by feature during future feature work to reduce change risk; preserve the pure domain and validation modules.
4. Add optional PNG/PDF/A3 export only if product requirements need those formats; keep SVG and print as the canonical full-resolution paths.
5. Test multi-tab concurrent editing and storage-pressure behavior in a browser lab because they cannot be faithfully simulated by unit tests alone.
